Wrap it.

Instruções adicionais: $ARGUMENTS

Determine o contexto a partir do histórico da conversa primeiro.

Regras para detecção de contexto:
- Se a conversa já mencionar uma issue ou PR do GitHub, use esse contexto existente.
- Se o trabalho veio de `/is` ou `/pr`, assuma que o contexto da issue ou do PR já é conhecido a partir da conversa e do trabalho de análise já realizado.
- Se não houver issue ou PR do GitHub no histórico da conversa, trate isso como um trabalho que não é do GitHub.

A menos que eu sobrescreva algo explicitamente nesta requisição, faça o seguinte na ordem:

1. Adicione ou atualize a entrada relevante do changelog do package em `## [Unreleased]` usando as regras de changelog do repositório.
2. Se esta tarefa estiver vinculada a uma issue ou PR do GitHub e um comentário final da issue ou PR ainda não tiver sido postado nesta sessão, rascunhe-o no meu tom, visualize-o e poste exatamente um comentário final. O comentário deve terminar com esta linha de aviso (disclaimer) isolada exata, sem variações:

   ```text
   This comment is AI-generated by `/wr`
   ```
3. Faça o commit apenas dos arquivos que você alterou nesta sessão.
4. Se esta tarefa estiver vinculada a exatamente uma issue do GitHub, inclua `closes #<issue>` na mensagem de commit. Se estiver vinculada a várias issues, pare e pergunte qual usar. Se não estiver vinculada a nenhuma issue, não inclua `closes #` ou `fixes #` na mensagem de commit.
5. Verifique a branch atual do git. Se não for `main`, pare e pergunte o que fazer. Não faça push de outra branch a menos que eu diga explicitamente para fazê-lo.
6. Faça push da branch atual.
7. Se esta tarefa estiver vinculada a exatamente uma issue do GitHub, feche essa issue explicitamente com o motivo (reason) `completed` após o push para que os workflows de fechamento de issue em `.github/` sejam executados. Isso se aplica apenas a issues, não a PRs.
   - Inspecione `gh issue view <issue> --json state,stateReason,labels`.
   - Se a issue estiver aberta, execute `gh issue close <issue> --reason completed`.
   - Se a issue já estiver fechada com qualquer motivo diferente de `COMPLETED`, reabra-a primeiro e, em seguida, feche-a com `gh issue close <issue> --reason completed` para que o GitHub emita um novo evento de fechamento.
   - Se a issue já estiver fechada como `COMPLETED`, deixe-a fechada a menos que a label `inprogress` ainda esteja presente; nesse caso, reabra-a e feche-a novamente com o motivo `completed`.

Restrições:
- Nunca faça stage de arquivos não relacionados.
- Nunca use `git add .` ou `git add -A`.
- Execute as verificações (checks) obrigatórias antes do commit se o código mudou.
- Não abra um PR a menos que eu solicite explicitamente.
- Se este não for um trabalho de issue ou PR do GitHub, não poste um comentário no GitHub.
- Se um comentário final de issue ou PR já foi postado nesta sessão, não poste outro a menos que eu solicite explicitamente.
- Ao trabalhar contra uma branch diferente de `main`, pule o changelog.
